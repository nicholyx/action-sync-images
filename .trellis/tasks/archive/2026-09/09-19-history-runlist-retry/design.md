# 设计：gh run list 的失败分类与重试

## 边界

只改 `scripts/history.sh` 的 `download_reports()`（`:261` 起）里的**运行列表获取**一段。不动下载重试（#97 已做）、不动 `classify_download_failure` / `confirm_artifact_exists`、不动退出码语义。

## 核心难点：进程替换拿不到退出码

现状：

```bash
done < <(gh run list "${list_args[@]}" 2>/dev/null || true)
```

进程替换 `< <(...)` **不传递退出码**——`$?` 是 `while` 的，不是 `gh` 的。这正是 `|| true` 存在的原因：不写它，`set -e` 也不会因为 gh 失败而退出（因为退出码根本没被检查）。于是：

```
网络 EOF → gh 非零退出 → 空输出 → run_ids 为空 → 落到「没有取到任何运行记录」
```

诊断方向被引到了完全错误的地方（让人去查「工作流是不是没跑过」）。

### 解法：先落临时文件，再读

`WORK_DIR` 在 `download_reports` 内已由 `mktemp -d` 创建并是全局可见（`:262`），直接复用，不新增临时文件管理：

```bash
  # gh run list 的退出码必须接住。进程替换 < <(...) 不传递退出码，
  # 原来那句 `2>/dev/null || true` 把失败与「空列表」彻底混成一种结果
  # （Issue #98，2026-09-16 真实踩到）——网络 EOF 时报的是「工作流没跑过」。
  local list_out="${WORK_DIR}/run-list.txt"
  local list_err_file="${WORK_DIR}/run-list.err"
  local list_rc=0
  gh run list "${list_args[@]}" > "$list_out" 2> "$list_err_file" || list_rc=$?

  if [[ "$list_rc" -ne 0 ]]; then
    log_warn "获取运行列表失败，重试一次（多为网络抖动）..."
    sleep 5
    list_rc=0
    gh run list "${list_args[@]}" > "$list_out" 2> "$list_err_file" || list_rc=$?
    [[ "$list_rc" -eq 0 ]] && log_info "重试成功"
  fi

  if [[ "$list_rc" -ne 0 ]]; then
    local list_err=""
    [[ -s "$list_err_file" ]] && list_err="$(head -n1 "$list_err_file")"
    die "获取运行列表失败（已重试一次）：${list_err:-未知错误}。多为网络原因，稍后重跑即可"
  fi

  local -a run_ids=()
  local id
  while IFS= read -r id; do
    [[ -n "$id" ]] && run_ids+=("$id")
  done < "$list_out"

  [[ ${#run_ids[@]} -gt 0 ]] || die "没有取到任何运行记录。请确认…（原文案逐字不变）"
```

### 四个要点

1. **stdout 与 stderr 分开落文件**。合到一处（`2>&1`）会让 gh 的报错混进 `databaseId` 列表，`read` 循环会把错误文本当成 id。
2. **路径与内容要分开**。`list_err_file` 是**文件名**，`list_err` 是**文件内容**。第一版草案直接写了 `die "...：${list_err}..."` 而 `list_err` 存的是路径，报错信息于是把临时文件路径当成错误原因打印出来——**这个错是跑 mock 用例时才暴露的**，纸面推演看不出来。命名上必须让两者一眼可分。
3. **只取 stderr 的第一行**（`head -n1`）。gh 的报错可能多行，整段塞进 `die` 会把单行错误信息撑成一段，反而看不清重点。
4. **重试后才判空**。判定顺序必须是「先看退出码，再看是否为空」——反过来的话，失败场景仍会掉进空列表分支。

## 口径：与 #97 保持一致

| 决策 | 取值 | 依据 |
| --- | --- | --- |
| 重试次数 | 1 轮 | 与 #97 的下载重试同口径；持续抖动不是脚本该解决的 |
| 间隔 | 固定 5 秒 | 与 #97 一致（`history.sh:326` 附近的既有实现） |
| 参数化 | **不做** | `history.sh:321-326` 的注释已确立：为极少调整的值增加表面积不划算，新参数还得进「显式传入不生效告警」矩阵 |
| 分类 | **不分类** | 这里不需要区分「网络问题」与「仓库问题」——重试一轮之后仍失败，如实说「多为网络原因，稍后重跑即可」即可，与 #87 的附件分类是两回事 |

## 不做的事

- **不重试 `--dir` 路径**：`--dir` 完全不碰 `gh`，本段代码在它前面就返回了
- **不改空列表文案**：那个诊断（「请确认当前目录在 GitHub 仓库中，gh 已登录，且工作流至少跑过一次」）在退出码为 0 时是**准确**的，PRD R3 要求逐字不变
- **不给失败分类加新函数**：与 #87 的 `classify_download_failure` 不同，这里不需要按文案分类——有退出码可用，比文案可靠

## 兼容性

| 影响面 | 说明 |
| --- | --- |
| `--limit` / `--workflow` 参数组装 | 不动，`list_args` 原样复用 |
| `run_ids` 数组的后续消费 | 不变，仍是「从 stdout 逐行读」 |
| 退出码 | 不变（`die` 仍是 1）；空列表、无附件等分支的判定顺序不变 |
| bash 3.2 | 无空数组展开、无 `wait -n`、无关联数组 |
| `WORK_DIR` 的生命周期 | 复用既有 `trap ... EXIT` 清理，不新增文件 |

## 回滚

单函数内的一段改动，revert 即回到「失败冒充空列表」的旧行为。无状态、无数据迁移。

## 验证方式

真实网络失败造不出来，走 **mock `gh`** —— CI `:1202-1290` 已有抽取 `download_reports` 整体 + mock 的完整骨架，直接扩展：

| 用例 | mock 行为 | 断言 |
| --- | --- | --- |
| A：首次失败后成功 | `run list` 第一次返回 1，第二次返回 id 列表 | 流程继续；日志含「重试」；`sleep` 计数 = 1 |
| B：两次都失败 | `run list` 恒返回 1 | `die`，退出码 1；文案含「获取运行列表失败」与「重试」 |
| C：空列表 | `run list` 返回 0 且无输出 | `die`，**文案与改动前逐字相同**（对照 PRD R3） |
| D：首次即成功 | `run list` 返回 0 + id 列表 | 不重试，`sleep` 计数 = 0 |

`sleep` 已被既有骨架 mock 成写文件计数（`:1231`），用例 A/D 直接复用该机制。

用例 C 的「逐字相同」断言要**先跑当前代码取基线**，再把同一串文案写进断言——不能凭记忆重写，那会变成「断言我改完之后的文案」，失去回归意义。

### 四个用例已用 mock 实测（2026-09-19）

上述代码片段已抽出来在 mock `gh` 下跑过，四个用例的实际表现：

| 用例 | 退出码 | `sleep` 次数 | `gh run list` 调用次数 | 输出 |
| --- | --- | --- | --- | --- |
| A 首次失败后成功 | 0 | 1 | 2 | 「重试一次」警告 + 「重试成功」 |
| B 两次都失败 | 1 | 1 | 2 | `获取运行列表失败（已重试一次）：Get "…": EOF。多为网络原因，稍后重跑即可` |
| C 空列表（退出码 0、无输出） | 1 | 0 | 1 | 原文案，**未触发任何重试** |
| D 首次即成功 | 0 | 0 | 1 | 输出 id 列表，无重试 |

用例 B 的输出是修正后（`head -n1 "$list_err_file"`）的结果。**修正前它打印的是临时文件的路径**——见上文「四个要点」的第 2 条。

用例 C 尤其值得注意：它同时断言了「退出码 0 + 空输出」**不触发重试**（`sleep` 计数为 0）——如果重试条件写成「`run_ids` 为空就重试」，这里会变成 1，而用例 C 会红。这正是它要守住的东西。
