# PRD：通知成功判定只看 HTTP 码，平台侧拒收被报成「已推送」

对应 issue：[#159](https://github.com/nicholyx/action-sync-images/issues/159)

## 问题

`sync.sh` 的通知发送用 `curl -o /dev/null -w '%{http_code}'`，**响应体被丢弃**，只判
`^2` 即认定成功。

而钉钉、飞书这类平台恰恰在 **HTTP 200 的响应体里**用 `errcode` / `code` 表示失败：

```
HTTP/1.1 200 OK
{"errcode":310000,"errmsg":"keywords not in content"}
```

于是**平台侧拒收会被报成「结果已推送到 dingtalk」**。

## 为什么这是本项目定义的那类问题

它报的是「推送到」这个动作发生了，而使用者理解的是「**送到了**」。与仓库反复记过的
两条同族：

- **错误的信息比没有信息更糟**——一个假的成功通知比不发通知更坏，因为收件人不再去看日志
- **恒真的断言比没有断言更糟**——这条判定对任何 HTTP 200 都成立，包括「对方明确拒绝了」

## 期望（验收标准）

- [ ] **AC1**：按平台解析响应体判定成败。钉钉看 `errcode`、飞书看 `code`、
      Slack 看纯文本 `ok`；非 0 / 非 `ok` 时**如实报失败**，并带出平台给出的原因
      （`errmsg` / 错误码文本）
- [ ] **AC2**：各平台的判定**分别实现**，不套用一个通用规则——响应体结构本就不同
      （钉钉/飞书是 JSON 且字段名不同，Slack 是纯文本 `ok`）
- [ ] **AC3**：**无法判定必须单独成类**，不能默认成功。响应体不是预期结构 / 不是 JSON 时，
      明确说「无法判定」，与「已送达」「被拒收」三者互不混淆
- [ ] **AC4**：断言覆盖——mock 一个「HTTP 200 + `errcode` 非 0」的响应，断言脚本**报失败**
      （不是报「已推送到」）。同批覆盖：HTTP 200 + `errcode` 0 → 报成功；响应体不是
      预期结构 → 报「无法判定」
- [ ] **AC5**：`notify_send_text` 的既有契约不变——**永远返回 0**。通知是附加能力，
      发不出去只告警，绝不能让一次成功的运行变红

## 边界（先判断再动手，来自 issue）

- **自建 webhook 返回 200 空体** → 必须**继续算成功**，不能因为「解析不了」就报失败
- **各平台错误码语义不同**（有的 `errcode`、有的 `code`、有的 HTTP 码本身就是全部）
  → 按平台分别处理，**不造统一抽象**
- webhook 地址视同凭证：日志里只记类型与结果，**绝不输出 URL**（既有约束，不变）
- 不改变「发不发」的门禁语义（`--notify-on` / `--notify-after-failures`）——本次只改
  「发出去之后怎么判定」

## 不做什么

- 不改 `--notify-on failure` 的发送门禁（那是 #158 的覆盖对象）
- 不引入重试、不改变超时
- 不为 generic 类型猜「什么是失败」——它没有可依据的契约
