# 架构文档补记 v1.13–v1.16 的设计决策

## Goal

把 v1.13–v1.16 四轮改动里「为什么这样而不是那样」的取舍补进 `docs/ARCHITECTURE.md` 的「关键设计决策」一节——它现在停在 **v1.11**。

## Background

这一节的定位写在项目自己的版本记录里（v1.12.0 的主题句）：

> 架构文档补齐……设计记录的价值在于**改设计前先确认不是把记录过的决定改回去**。

而 v1.12.0 的整个主题就是「文档同步」——说明这件事在本项目里不是可选项。当时的做法是「按版本时序补六个为什么，每个小节的论断逐条对照代码核过」。

**v1.13 到 v1.16 又积累了四轮改动，其中多个决策正是「容易被改回去」的类型**：它们看起来像是可以「优化」的地方，但当初不做成那样是有原因的。这些原因目前只散落在代码注释、CHANGELOG 与 PR 描述里。

### 现有覆盖

| 版本 | 是否有「为什么」记录 |
| --- | --- |
| v1.13 dry-run 计划预览 | ✅ 已有（「为什么 dry-run 先输出同步计划预览」，`:361`） |
| v1.14 报告下载的批量重试 | ❌ 缺 |
| v1.15 失败后的可操作化（note / 重跑指引 / run list） | ❌ 缺 |
| v1.16 dry-run 的诚实性（含 v1.16.1 的报告隔离） | ❌ 缺 |

## Requirements

- **R1** 补记以下决策，每条给出**核心理由**与**被否方案或代价**（与既有条目同构）：

  | # | 决策 | 容易怎样被改回去 |
  | --- | --- | --- |
  | 1 | 报告下载的重试为什么放在主循环之后、只重试一轮、且不做参数化 | 会有人想加 `--retry-times`/`--retry-delay` 参数，或改成逐次重试 |
  | 2 | 失败原因为什么必须进报告、Summary 与通知 | 会有人觉得「终端已经打了，报告里重复」 |
  | 3 | 重跑指引为什么排除「镜像引用格式错误」的项 | 会有人觉得「失败项都该列进去，少列就是漏」 |
  | 4 | `gh run list` 的失败为什么重试一轮后再报错，而不是直接失败 | 会有人觉得「网络错误立刻报就好，重试是多余开销」 |
  | 5 | dry-run 的判据为什么是「**有没有真的搬过**」而不是「这段代码跑了多久」 | 会有人把计时守卫当成冗余的 if 删掉 |
  | 6 | dry-run 下锁文件与通知为什么是「不生效 + 告警」，而不是产出「dry-run 版」 | 会有人觉得「应该照常生成，标注一下就行」 |
  | 7 | 报告为什么加 `dry_run` 字段，而不是改 `status` 的取值 | 会有人觉得「加字段不如直接让 status 说清楚」 |

- **R2** 每条论断**必须有原始依据**（代码注释 / PR 描述 / CHANGELOG），逐条对照核过；**不得杜撰理由**。找不到依据的宁可不写
- **R3** 格式与既有条目一致：「### 为什么 X」+ 首句加粗给出核心理由 + 展开说明
- **R4** 插在「关键设计决策」一节内**按版本时序**（既有条目已是时序排列）
- **R5** 同步更新该文件的目录（若有列这些条目）与 `README` 中若有指向该节的描述
- **R6** 不改任何代码

## Acceptance Criteria

- [ ] 七条决策（或说明为何合并/舍弃某条）已补进「关键设计决策」
- [ ] 每条都能在代码注释 / CHANGELOG / PR 里找到依据（在提交说明或复核中可核对）
- [ ] 格式与既有条目一致（标题句式、加粗首句）
- [ ] 时序正确：v1.14 在 v1.13 之后、v1.16 在最后
- [ ] 文档内部链接与目录未被打断
- [ ] 全仓无 U+FFFD 与控制字符；`./scripts/lint.sh` 全绿

## Out of Scope

- **不重写既有条目**（v1.11 以前的）
- **不改 ARCHITECTURE 的其他小节**（代码结构、安全模型等）
- **不做「代码与文档全面对账」**——本任务只补设计决策这一节；如果过程中发现别处过时，**记录并单独提出**，不顺手改（避免把一次可复核的改动变成不可复核的大改）
- **不动 `docs/USAGE.md` / `TROUBLESHOOTING.md`**（它们面向使用者，已在各轮改动中同步）
