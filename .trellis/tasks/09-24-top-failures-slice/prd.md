# 补 --top-failures 的「最多显示 N 条」效果断言

对应 Issue：nicholyx/action-sync-images#157

## Goal

`--top-failures` 的断言目前只覆盖「**CLI → 变量 → 报告的 `query` 字段**」这条通路，
**不覆盖切片的实际效果**。

检查阶段实测：把 `history.sh` 的切片写死成 `[:10]`（忽略变量、永远显示 10 条），
**断言仍然全绿**。

**即：参数传进去了有断言，「最多显示 N 条」没有。** 而后者才是这个参数的**语义**。

## 现状（已确认）

```bash
rows="$(jq --argjson n "$TOP_FAILURES" '[.[] | select(.fail > 0)][:$n]' <<<"$rows")"
```

选 `fail > 0` 的记录，取前 N 条。

## Requirements

### R1 两侧都要断言

| 场景 | 期望 |
| --- | --- |
| **失败数 > N**（如 5 条失败 + `--top-failures 2`） | 报告里**恰好 2 条** |
| **失败数 < N**（如 5 条失败 + `--top-failures 10`） | **5 条都在**（切片不该把不足的量也截掉） |

**用「恰好 N 条」而不是「不超过 N 条」**——「少显示了」同样是错的，
而「不超过」会把它算过。

### R2 夹具要能区分「切了」与「没切」

夹具要有**至少 5 条** `fail > 0` 的记录。少于这个数的话，`[:2]` 与不切片的输出
**长度相同**，断言就恒真了。

**这点必须实测确认**：构造完夹具后，先用「不切片」的实现跑一遍，确认输出条数与
「切到 2 条」**不同**。相同就说明夹具选得不对。

### R3 夹具型断言要双向可信

按 `.trellis/spec/engine/index.md` 的既有要求：夹具里放**正对照**，断言用**等值**。
本任务的「失败数 < N」那条天然就是正对照（它证明夹具真的被读进去了）。

## Acceptance Criteria

- [ ] **AC1** 「失败数 > N → 恰好 N 条」有断言
- [ ] **AC2** 「失败数 < N → 全部都在」有断言
- [ ] **AC3** 夹具**实测**能区分「切了」与「没切」（R2 的要求，要有数据）
- [ ] **AC4** **变异验证**：把切片写死 `[:10]` → AC1 那条必须红
- [ ] **AC5** **变异验证**：把切片改成「不切」→ AC1 那条也必须红
- [ ] **AC6** `bash -n`、`shellcheck`、`./scripts/lint.sh` 全绿；CI 全部 job 全绿

## Constraints

- **不改生产代码**（只加断言）
- **不要写否定式判据**（「不超过 N 条」就是——它把「少显示了」算过）
- 兼容 bash 3.2
- 手写夹具（与同批其它 `history.sh` 用例一致，不需要网络/容器）

## Out of Scope

- `--top-failures` 的**特例分支**（后跟选项/结尾时退回默认值）—— 已在 PR #160 覆盖
- 切片的**排序**（`fail` 降序）—— 若发现它也没断言，在报告里说，另开

## Notes

- 判据是「**这个参数的效果**」而不是「这个参数的通路」——参数传进去只是第一步，
  「最多显示几条」才是它要做的事
- 这与本项目反复记过的那类问题同族：**「参数被接受」与「参数起作用」是两件事**
