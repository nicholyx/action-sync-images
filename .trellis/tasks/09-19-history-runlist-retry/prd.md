# gh run list 网络失败被吞掉，误报「没有取到任何运行记录」

## Goal

在 `scripts/history.sh` 里把 `gh run list` 的**请求失败**与**空列表**区分开：前者重试一轮，仍失败则报网络问题；后者保留现有文案。

对应 Issue [#98](https://github.com/nicholyx/action-sync-images/issues/98)。

## Background

### 现状

`scripts/history.sh:279`：

```bash
done < <(gh run list "${list_args[@]}" 2>/dev/null || true)
```

`2>/dev/null || true` 把退出码彻底吞掉。网络 EOF 时得到空输出 → `run_ids` 为空 → 落到 `:281`：

```bash
die "没有取到任何运行记录。请确认当前目录在一个 GitHub 仓库中，gh 已登录，且工作流…至少跑过一次"
```

**真实踩到**（2026-09-16 验证 #97 的下载重试时）：明明有运行记录，换一次网络就查到了，而报错引导人去怀疑「工作流没跑过」。

这与 [#87](https://github.com/nicholyx/action-sync-images/issues/87)（下载失败冒充「无附件」）同族：**网络问题被冒充成「数据不存在」**。同一个函数内的 `gh run download` / `gh api` 在 v1.11 已按此原则分类，`gh run list` 是漏网的第三处。

### 已定的决策（2026-09-18）

**重试一轮，再报网络错。** 理由：

- 网络抖动是这条路径的常态，重试能真的省掉一次人工重跑
- 与 #97 的重试思路一致（同一文件、同一类问题），且已有骨架可参照（`scripts/history.sh:283-341`）
- 只重试一轮、固定间隔、**不做参数化**——#97 的注释（`:321-326`）已确立这个口径：为极少调整的值增加表面积不划算

## Requirements

- **R1** `gh run list` 非零退出时，**重试一轮**
- **R2** 重试仍失败 → 报错文案指向**网络问题与重试**，而不是「工作流没跑过」
- **R3** 真正的空列表保留现有文案（那个诊断是准确的）
- **R4** 退出码语义不变
- **R5** 不新增命令行参数

## Acceptance Criteria

- [ ] `gh run list` 失败时不会落到「没有取到任何运行记录」那条报错
- [ ] 重试成功时流程继续，且使用者能看出「重试过一次」
- [ ] 空列表（gh 成功但无输出）仍报现有文案，措辞不变
- [ ] 重试仍失败时，报错文案指向网络与重试
- [ ] macOS 自带 bash 3.2 下正常（无空数组展开、无 `wait -n`）
- [ ] CI 有对应断言；断言**先在本地复现**过

## Out of Scope

- 不改 `gh run download` / `gh api` 的既有分类逻辑（v1.11 已做）
- 不给重试次数/间隔加参数（与 #97 同口径）
- 不动报告下载的重试路径
