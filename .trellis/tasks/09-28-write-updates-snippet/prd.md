# PRD：`--check-updates` 生成可粘贴的清单片段

对应 issue：[#169](https://github.com/nicholyx/action-sync-images/issues/169)（里程碑 v1.20.0）

## 问题

`--check-updates` 回答「上游有哪些 tag 不在清单里」，但它**只报告**——这是刻意的立场
（文档写明「只报告，**不修改清单**——升到哪个版本涉及兼容性判断，是人的决定」）。

立场没问题，但**从报告到清单之间那一跳现在全靠手工**：多仓库 × 多 tag 时，使用者要盯着
屏幕一行行把 tag 抄进 `images.lock.txt`，还要给每一行拼上仓库名。抄错一个字符就是下一次
同步失败。

## 期望（验收标准）

- [ ] **AC1**：新增 `--write-updates <路径>`，与 `--check-updates` 同用，写出形如
      `registry.k8s.io/pause:3.10` 的行——**与 `--file` 读取的格式完全兼容**，
      生成的文件可直接 `--file` 喂回脚本
- [ ] **AC2**：**写全部未收录的 tag，不受 `--updates-limit` 影响**。`--updates-limit`
      的口径是「只限制展示条数，不改变总数」（#158 的断言守着这条）；文件是「要加就加全」。
      **屏幕与文件的条数不同时，日志要说明这一点**——否则使用者会以为上游只有 5 个新 tag
- [ ] **AC3**：内容分组可读——按仓库分组，每组一行 `# <仓库>` 注释（清单格式支持 `#` 行内注释），
      组内按**版本序升序**（人读的顺序；屏幕上仍是降序取前 N）
- [ ] **AC4**：**不修改任何既有文件**。原清单字节不变
- [ ] **AC5**：没有未收录 tag 时**仍然写出文件**，头部注明「没有需要补充的 tag」——
      「文件不存在」与「没有要加的」不能混成一种
- [ ] **AC6**：只在 `--check-updates` 下生效。其他模式（同步 / `--audit` / `--audit-lock`）
      显式传入时进该模式的「本次不生效」合并告警（仓库既有约定：显式传入却不生效必须说出来）
- [ ] **AC7**：日志报出「已写入 <路径>（N 行）」；文件内容与报告列出的 tag **同源**
      （同一批数据，不许两处各自算）

## 边界（先判断再动手）

- **不造「自动改清单」**：生成的是**建议**，合并仍由人做。这是本任务的边界，不是疏漏
- 与 `--report-dir` 的关系：两者都是写文件，但一个写给机器、一个写给人粘贴 —— **不合并成一个参数**
- 写文件失败（目录不存在 / 不可写）的处置：**先核实 `--report-dir` 与 `--write-lock` 的既有口径**
  （前者中断、后者告警），再决定跟哪一个，并在 PR 里说明理由。**不要凭直觉选**
- `--updates-limit` 的展示口径一个字不改——本任务只新增一个输出通道

## 不做什么

- 不修改清单文件（红线）
- 不引入新的存储
- 不改通知内容（`notify_detail` 那一段保持原样）

## 风险

- `UPD_REPOS` 存的是 `REF_REPO`（带 registry 前缀的完整仓库名），拼 `<repo>:<tag>` 时要注意
  **不要重复拼接 tag**（源引用可能已带 tag 或 digest）
- 排序：屏幕用 `sort -Vr`（版本序降序），文件要升序——**同一个 `sort -V` 换个方向**，
  不要另写一套比较（两处口径分家就是「同一个概念有两份实现」的种子）
- 断言要覆盖「原文件没被改」——这是本任务最容易写漏、也最要紧的一条
