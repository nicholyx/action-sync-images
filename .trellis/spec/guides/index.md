# 设计原则（跨模式的判断依据）

新功能「该不该做、怎么做」发生分歧时，按这里的既有判断对齐。
每条都在本仓库的真实迭代里被验证过，出处见标注。

## 1. 错误的信息比没有信息更糟，因为它会被当成结论

- 「无法判定」在所有检查里单独成类，判据刻意保守（`probe_ref`：只有 registry 明确回答「不存在」才下缺失/删除的结论）
- 与 `--strip-attestation` 互斥且直接报错（而非告警后继续）——能预见输出会误导人时，就拒绝执行
- 参数被接受却不生效必须告警（默认值不生效不打扰，显式传入必须说）

## 2. 排除/筛掉的东西必须可见

被 `--filter`/`--exclude` 排除的镜像出现在结果表并标注原因；锁文件的标注行原样带出。
**悄悄消失是最危险的**——使用者会以为它同步了。

## 3. 只报告，不替使用者做判断

`--check-updates` 只列「上游有这个 tag 而清单没有」，绝不说「该升级到哪个版本」；
不做语义化版本比较、不过滤预发布（上游命名不规整，比较会给出错误结论）。
升不升级、锁不锁新 digest，是人的决定——与「同步必须显式触发」同源。

## 4. 检查与搬运分开

只读的问题不该需要写权限。「我的仓库跟上清单了吗」在 `--audit` 出现之前只有真跑一次同步才能回答。
新能力先问：这是检查（可只读）还是动作（有副作用）？两者不要混在一条命令里。

## 5. 不引入新的存储

历史趋势读报告 Artifact（30 天窗口，足够回答「是不是一直在失败」）；连续失败次数从历史报告推算；
检查报告复用同一 Artifact 机制。需要跨运行状态时先问：**已有数据源能不能回答？**

## 6. 凭证不进命令行、不进日志

写进 600 权限临时文件（authfile），脚本退出即删；CI 用环境变量传参。
源与目标凭证刻意分开——把目标凭证发给源仓库等于交出推送权限。
webhook URL 视同凭证。`${{ }}` 不直接进 `run:`（表达式注入）。

## 7. 优化必须是有边界的纯优化

多目标的本地 OCI 中转：准备阶段任何失败都退化为旧行为（逐目标拉推），结果记录语义不变。
单目标不走中转——**没有收益的改动不该做**。优化不得引入故障传染（被否掉的方案：以第一个目标为中转）。

## 8. 失败要能定位到最小单元

多目标逐目标独立判定与记录；批量同步单镜像失败不影响其余；「每个镜像 × 每个目标」是一条独立记录。
优化与聚合都不能抹掉这一层。

## 9. 兼容性是硬约束

macOS 自带 bash 3.2 是一等公民（见 [engine/bash-rules.md](../engine/bash-rules.md)）。
CI 的 bash 5 掩盖不了 3.2 的差异——「CI 绿」不等于「本地没问题」。
