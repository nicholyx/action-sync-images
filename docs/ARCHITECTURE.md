## 这个项目解决什么问题

国内集群拉取国外镜像仓库（`registry.k8s.io`、`gcr.io`、`quay.io`、`ghcr.io`）时会遇到网络不可达。

常见的三种绕法，各有各的麻烦：

| 做法 | 问题 |
| --- | --- |
| 用别人同步好的镜像 | 版本掌握在别人手里，你要的版本可能没有；也不知道对方同步的是不是原版 |
| 自己买台海外 VPS 做中转 | 要花钱、要维护，还得手动 `pull` / `tag` / `push` |
| 用阿里云的镜像服务做拉取 | 单次操作、不方便批量，也不便于纳入版本管理 |

本项目走的是第四条路：**把 GitHub Actions 当作一台免费的、临时的中转机**。

运行器在海外，能直接访问所有上游仓库；我们把镜像从一个 registry 搬运到另一个 registry，全程不需要你拥有任何服务器，也不依赖第三方是否同步过。

## 整体架构

```text
┌──────────────────────────────────────────────────────────────────┐
│ 触发方式                                                          │
│   ├─ workflow_dispatch   手动触发（主路径，按需同步单个/多个镜像）  │
│   └─ schedule            定时批量（读取清单文件，默认关闭）         │
└──────────────────────────────┬───────────────────────────────────┘
                               ▼
┌──────────────────────────────────────────────────────────────────┐
│ .github/workflows/sync-images-*.yml                              │
│                                                                  │
│ 职责边界（刻意保持得很薄）：                                        │
│   • 登录目标仓库（读取 Secrets）                                   │
│   • 把 workflow_dispatch 的输入经 env 中转后组装成命令行参数         │
│   • 调用 scripts/sync.sh                                          │
│   • 上传同步报告为 Artifact                                        │
│                                                                  │
│ 这里**不含任何同步逻辑**。                                         │
└──────────────────────────────┬───────────────────────────────────┘
                               ▼
┌──────────────────────────────────────────────────────────────────┐
│ scripts/sync.sh  ← 全项目唯一的同步逻辑实现                         │
│                                                                  │
│   1. 解析输入：拆分批量镜像、去重、校验引用格式                       │
│   2. 选择路径：skopeo 还是 regctl                                  │
│   3. 执行同步：必要时自动探测平台、失败重试                          │
│   4. 产出报告：控制台表格 / GitHub Step Summary / JSON+Markdown     │
└──────────────────────────────┬───────────────────────────────────┘
                               ▼
                 ┌─────────────┴─────────────┐
                 ▼                           ▼
      ┌────────────────────┐      ┌────────────────────────┐
      │  skopeo copy --all │      │  regctl index create   │
      │                    │      │                        │
      │  默认路径           │      │  剔除 attestation 路径  │
      │  原样搬运整个索引    │      │  只保留指定平台的子镜像  │
      └────────────────────┘      └────────────────────────┘
```

**为什么要把逻辑抽到 `scripts/sync.sh`？**

因为本地和 CI 需要同一套行为。如果工作流里写一份、本地脚本再写一份，两边迟早会漂移——某天你会发现「CI 里能跑通的参数，本地跑就是不行」。把逻辑收敛到一处，本地能用 `--dry-run` 快速验证，CI 只是换了个执行环境而已。

代价是工作流需要 `actions/checkout` 把脚本拉下来。这个代价是值得的。

## 一次同步的完整流程

以「把 `registry.k8s.io/coredns/coredns:v1.11.1` 同步到阿里云」为例。

### 1. 触发

在 Actions 页面选择 `Sync-Images-to-AliYuncs`，点击 Run workflow，填写：

```text
images_src:        registry.k8s.io/coredns/coredns:v1.11.1
strip_attestation: false
platforms:         （留空）
dry_run:           false
```

### 2. 登录目标仓库

工作流执行：

```bash
registry_host="${DEST_REGISTRY%%/*}"     # → registry.cn-shenzhen.aliyuncs.com
printf '%s' "$REGISTRY_PASSWORD" | docker login "$registry_host" --username "$REGISTRY_USERNAME" --password-stdin
```

登录成功后，凭证被写进 `~/.docker/config.json`。

**这一步是后面所有工具能推送的前提**：`skopeo` 和 `regctl` 都会自动读取这个文件里的认证信息，因此不需要再单独为它们配置凭证。有人会问「为什么用 `docker login` 而不是 skopeo 自带的 `--dest-creds`」——因为这样能保证登录地址和推送地址永远来自同一个变量，改仓库时不会漏掉任何一处。

### 3. 组装参数并调用同步脚本

```bash
args=(--src "$IMAGES_SRC" --dest "$DEST_REGISTRY" --report-dir ./reports)
if [[ "$STRIP_ATTESTATION" == "true" ]]; then args+=(--strip-attestation); fi
if [[ -n "$PLATFORMS" ]];        then args+=(--platforms "$PLATFORMS"); fi
./scripts/sync.sh "${args[@]}"
```

注意所有 `${{ inputs.* }}` 都先经 `env:` 落到环境变量，再在脚本里引用。**绝不能**直接写 `${{ inputs.images_src }}` 到 `run:` 里——那等于把用户输入直接拼进 Shell 脚本，是教科书级的表达式注入。

### 4. sync.sh 内部做了什么

```text
解析参数
   │
   ├─ 校验：--dest 和 --dest-exact 至少给一个
   ├─ 规范化：去掉可能误带的 docker:// 前缀和结尾斜杠
   │
   ├─ 检查依赖：skopeo 必须存在；jq 可选；strip 模式下才需要 regctl
   │
   ├─ 收集镜像列表
   │     ├─ 把逗号 / 分号 / 换行分隔的输入拆成一行一个
   │     ├─ 从 --file 指定的清单文件里读（剥掉注释与空白）
   │     ├─ awk 去重，保持原有顺序
   │     └─ --filter / --exclude 正则筛选（被排除的仍占位，见「关键设计决策」）
   │
   ├─ 装载源仓库凭证（如有）：解析映射文件或单值凭证 → 600 权限临时 authfile
   │
   └─ 逐个处理（--concurrency 大于 1 时并发执行）：
         ├─ 校验引用格式（拦住 URL、缺 tag 这类明显错误）
         ├─ 计算目标地址
         ├─ 第一遍：逐目标增量跳过判定，收集真正需要推送的目标
         ├─ 多个目标待推送 → 源拉取一次到本地 OCI 目录，逐目标推送（失败自动退化）
         ├─ 决定平台列表
         ├─ 执行同步（带超时保护，用 ::group:: 折叠输出）
         ├─ --verify 时逐平台比对源与目标的子 manifest digest
         └─ 记录结果到独立文件（全部结束后按序读回，保证顺序稳定）

产出：
   ├─ 控制台表格（stderr）
   ├─ $GITHUB_STEP_SUMMARY（Actions 页面直接渲染成表格 + 最慢记录排行）
   └─ reports/sync-report.{md,json}
```

### 5. 结果呈现

三层输出，对应三种使用场景：

| 输出 | 给谁看 | 在哪看 |
| --- | --- | --- |
| 控制台表格 | 盯着日志排错的人 | Actions 日志 |
| Step Summary | 只想确认「成了没」的人 | Actions 运行页面顶部 |
| Markdown / JSON 报告 | 需要存档或二次处理的人 | Artifact 下载 |

退出码有明确语义，便于被其他工具调用：

| 退出码 | 含义 |
| --- | --- |
| `0` | 全部成功 |
| `1` | 参数或环境错误（缺依赖、参数非法）——根本没开始同步 |
| `2` | 至少一个镜像同步失败——其他镜像仍然会继续尝试 |

## 两条同步路径

### 默认：`skopeo copy --all`

```bash
skopeo copy --all \
  --retry-times 3 \
  docker://registry.k8s.io/coredns/coredns:v1.11.1 \
  docker://registry.cn-shenzhen.aliyuncs.com/nicholyx/registry.k8s.io_coredns_coredns:v1.11.1
```

`--all` 是关键：**没有它，只会同步运行器所在的 amd64 单平台**。加了它，源镜像如果是 multi-arch 索引，所有平台的子镜像和索引结构会被完整保留。

这是绝大多数情况下的正确选择，不依赖额外工具，速度也最快。

### 特殊：`regctl index create`

```bash
regctl index create <目标> \
  --ref <源镜像> \
  --platform linux/amd64 \
  --platform linux/arm64
```

这个路径只做一件事：**重建一个不含 attestation 的索引**。

它会把源索引里指定平台的子镜像逐个复制到目标仓库，然后重新组装一个新的 manifest 索引。因为只复制了列出来的平台，`platform` 为 `unknown` 的 attestation manifest 自然就不会被包含进去。

实际执行时前面还会多两样东西（`--tls-verify false` 与源凭证各带来一个，见下文「关键设计决策」）：

```bash
env DOCKER_CONFIG=<临时目录> \
regctl --host reg=<源仓库>,tls=disabled --host reg=<目标仓库>,tls=disabled \
  index create <目标> --ref <源镜像> --platform linux/amd64 …
```

两者都**不写任何配置文件**，跑完即弃。

### 怎么选

| 情况 | 用哪条 |
| --- | --- |
| 普通镜像 | 默认（skopeo）即可 |
| 同步时报 `unknown manifest class` 之类的错 | 改用 regctl，勾选「剔除 attestation」 |
| 源镜像来自 `netbirdio` 这类开启了 provenance 的项目 | 直接用 regctl |

## 深入理解 attestation 问题

这是本项目最容易被误解的地方，值得单独讲清楚。

### 什么是 attestation

较新的构建工具（BuildKit 等）在推镜像时，除了各平台的镜像本身，还会额外推两种「附件」：

- **provenance**：这个镜像**是怎么构建出来的**（用了哪个 Dockerfile、哪些构建参数）
- **SBOM**：镜像里**包含哪些软件包**

它们以符合 OCI 1.1 规范的 manifest 形式存在，`platform` 字段被标记为 `unknown`，用来和真正的平台镜像区分开。

### 为什么会同步失败

这些附件在 OCI 1.1 里允许「空 blob」（即 `config` 大小为 0 的条目）。

阿里云 ACR 的校验逻辑还不支持这种形式，遇到时会直接拒绝，报错信息大致是：

```text
unknown manifest class for ...
```

而这个错误发生在推送整个索引的过程中，**会导致整个镜像同步失败**——哪怕你真正想要的那两个平台镜像完全正常。

### 为什么不能简单地「过滤掉」

因为 attestation manifest 是嵌在源索引里一起被引用的。你用 `skopeo copy --all` 时，它会忠实地把整个索引连同附件一起搬过去，没有「只搬一部分」的选项（skopeo 的 `--all` 是全有或全无）。

所以只能换一条路：**不搬运原索引，而是自己重新组装一个**。这正是 `regctl index create` 做的事——它按你给的平台列表逐个复制，然后新建索引。

### 代价

重建索引意味着你要**明确知道源镜像有哪些平台**。如果源镜像只有 `linux/amd64`，而你按默认的 `linux/amd64,linux/arm64` 去重建，regctl 找不到 arm64 的子镜像，就会失败。

针对这个问题，`sync.sh` 做了自动探测：

```text
如果用户显式指定了 --platforms → 用用户指定的
否则                             → 用 skopeo inspect --raw 读取源索引，解析出平台列表
                                   → 探测失败才回退到 linux/amd64,linux/arm64
```

探测逻辑依赖 `jq`，并且只对真正的 multi-arch 索引有效（单平台镜像的 manifest 里没有 `manifests` 字段，解析结果为空，会走回退分支）。

## 目标镜像名是怎么来的

这是使用中最容易困惑的部分。项目提供两种模式。

### 前缀模式（`--dest`，默认）

最终目标 = **前缀** + `/` + **源镜像路径中的 `/` 全部替换为 `_`**

```text
前缀：  registry.cn-shenzhen.aliyuncs.com/nicholyx
源镜像：registry.k8s.io/coredns/coredns:v1.11.1
        └──────┬──────┘ └──┬──┘ └──┬──┘
               │            │      └─ 保留原样
               └────────────┴────────┐
                                     ▼
目标：  registry.cn-shenzhen.aliyuncs.com/nicholyx/registry.k8s.io_coredns_coredns:v1.11.1
```

**为什么要做这种「压平」？** 因为阿里云容器镜像服务的个人版不支持多级仓库路径。你没法创建 `nicholyx/registry.k8s.io/coredns/coredns` 这样的仓库，但可以创建 `nicholyx/registry.k8s.io_coredns_coredns`。

把 registry 域名也保留在名字里，是为了避免不同来源的同名镜像互相覆盖——`registry.k8s.io/pause` 和 `docker.io/pause` 会被区分成两个仓库。

### 精确模式（`--dest-exact`）

目标地址由你完全指定，脚本不做任何拼接：

```text
--dest-exact harbor.example.com/library/nginx:1.27
源镜像         nginx:1.27
                │
                ▼
目标           harbor.example.com/library/nginx:1.27
```

适合自建 Harbor 这类支持多级路径的仓库。**注意这个模式只能搭配单个源镜像**——因为一个目标地址无法同时对应多个源镜像，脚本会明确报错而不是做出含糊的行为。

## 关键设计决策

以下是几个「当初为什么这么选」的记录。改代码前建议先读一遍。

### 为什么把同步逻辑放在脚本里，而不是直接写在 workflow 的 `run:` 中

**因为需要本地可验证。**

写在 `run:` 里的 Shell，只有推上去跑一次才知道对不对。抽成脚本后，可以用 `--dry-run` 在本地确认命令拼接是否正确，也可以在 CI 里做冒烟测试（`ci.yml` 的 `smoke-test` 任务就是干这个的）。

### 为什么 dry-run 先输出同步计划预览

**因为使用者需要先回答「这次会推到哪」，再决定要不要放行。**

只打印单条命令时，批量、筛选、多目标组合后的总数不够直观；尤其是 `--dest` 与 `--dest-keep-path` 混用时，很容易只确认第一个目标。计划预览把筛选后的源镜像、目标数量、预计命令数和每条源 → 目标映射摊开，并同步写进 Step Summary。

实现上刻意复用 `apply_filters` 之后的镜像数组和 `resolve_dest_refs`，**不重新解析输入**。如果计划独立拼一份目标地址，它迟早会和实际执行漂移——这正违背 dry-run 的价值。

计划也不预测「能不能跳过」或「自动探测出了哪些平台」：这些结果需要访问 registry，且属于实际执行阶段的事实。虚构它们会让预览看起来更完整，但更危险。被否掉的方案因此有两类：独立重新解析输入，以及在 dry-run 阶段做网络探测来填充更多细节。

### 为什么默认不做 attestation 剔除

**因为 `skopeo copy --all` 更快、更可靠，且能完整保留索引结构。**

把剔除做成默认行为会带来两个问题：一是每次同步都要先探测平台、再逐个复制，慢得多；二是会改变镜像的索引结构，对使用者来说是个意外。让需要的人显式勾选，是更诚实的设计。

### 为什么目标仓库地址做成变量而不是写死

**因为「改一处、漏一处」是这类项目最典型的故障。**

最初地址散落在三个地方（两处 `echo`、一处实际推送）。一旦只改了日志里的输出而漏掉真正推送的那处，就会出现「日志显示同步到了 A 仓库，实际推到了 B 仓库」——这是最难排查的一类问题。现在收敛成单个 `DEST_REGISTRY`，日志和实际行为必然一致。

### 为什么 `regctl` 版本要固定

**因为可复现性。**

原先用的是 `releases/latest/download`，意味着同一条工作流今天跑和明天跑可能用的是不同版本的工具。一旦新版本改了行为，你会看到一个「什么都没改但突然失败了」的工作流。现在固定为明确版本，升级是显式的、可追溯的（Dependabot 会提 PR）。

### 为什么 regctl 路径的 TLS 走 `--host`、凭证走临时 `DOCKER_CONFIG`

**因为这两样在 regctl 上根本没有同一个入口，而两个入口各带一个陷阱。**

默认路径（skopeo）有 `--src-tls-verify=false` 与 `--src-authfile` 两个现成参数，regctl 却把两件事都收在 registry 配置里：

- **TLS** 用 `--host reg=<host>,tls=disabled` 逐命令注入。它是**叠加**语义——注入的值不写进任何文件，使用者在 `~/.regctl/config.json` 里给别的仓库配的 `cacert` 与凭证原样保留
- **凭证**用临时 `DOCKER_CONFIG` 目录。regctl 没有 `--src-authfile` 这样的入口，它按 Docker 的规矩读 `$DOCKER_CONFIG/config.json`；目录里的 `config.json` 是使用者的 docker 配置与 `SRC_AUTHFILE` 的**递归合并**

被否掉的方案有三个，理由各不同：

1. **`REGCTL_CONFIG` 指向临时配置**——它是**替代**语义。实测把该变量指向另一份配置后，使用者原有的 host 配置**全部消失**。要用它就得自己读并合并用户的配置，那还不如 `--host` 叠加干净
2. **`--host reg=…,user=…,pass=…` 传凭证**——regctl 确实支持，实测也真的生效。但这违反项目在源凭证构造处定下的原则：凭证不进命令行（`ps aux` 可见），而 `--dry-run` 还要原样打印命令。硬走这条路，dry-run 就只能在「如实打印」与「打码」之间二选一——前者泄漏，后者违反 dry-run 铁律
3. **直接写使用者的 `~/.regctl/config.json` 或 `~/.docker/config.json`**——既污染全局配置，并发运行时还会互相覆盖

凭证那块**必须合并**、不能只放源凭证：`DOCKER_CONFIG` 与 `REGCTL_CONFIG` 一样是替代语义，只放源凭证会让使用者在**目标仓库**的 `docker login` 凭证消失——「修好了源、弄坏了目标」，比原来那个缺陷更隐蔽。

最后，`--tls-verify false` 在这条路径上映射为**明文 HTTP**（`tls=disabled`）：regctl 的 `tls` 是单值，`disabled` 管明文 HTTP、`insecure` 管自签证书，一个值照顾不了 skopeo 同时覆盖的两种场景。选前者是因为 regclient 对「连不上」给出的建议就是 `--tls disabled`，而明文 HTTP 是更常见的动机；自签证书的使用者会被一条告警指引到 `~/.regctl/config.json`。

Docker Hub 的三个别名（`docker.io` / `index.docker.io` / `registry-1.docker.io`）**不注入**。regclient **认**这个名字——`--host reg=docker.io,tls=disabled` 会以 `hostname=registry-1.docker.io`、`tls=disabled` 发请求，于是本该走 HTTPS 的 Docker Hub 被改成明文。它不会直接失败（实测：明文请求拿到 `301 Moved Permanently`，regclient 跟着重定向回 HTTPS，最终照常 200，只多出一次明文请求与一次重定向），所以这不是「不跳就会坏」。真正的理由是这笔代价**没有任何收益**——Docker Hub 的证书本就正常——却把「出站 80 端口可用」变成了 Docker Hub 源的前提，端口被挡的环境里就会真的连不上。代价是 Docker Hub 源拿不到「不校验证书」，而它在修复前也拿不到，不构成回归。

### 为什么 `--dest-exact` 不允许多镜像

**因为含糊的行为比报错更糟。**

如果要支持「多个源映射到多个精确目标」，就需要引入映射文件或成对参数，复杂度陡增。而如果只是简单地把它们全推到同一个地址，就会互相覆盖——用户看到的会是「同步成功了，但镜像不对」。让脚本明确报错并提示改用前缀模式，是更好的选择。

### 为什么用增量跳过，而不是每次全量推送

**因为重复推送是纯粹的浪费，而「跳过」比「推送」快几个数量级。**

同步镜像的时间几乎全花在网络传输上。定期同步的场景里，绝大多数镜像其实没有任何变化，却每次都要重新传一遍。开启 `--skip-existing` 后，脚本先比对源与目标的 manifest，相同就跳过——一次运行从几分钟缩短到几秒。

比对方式是**规范化后的 JSON 相等性**，而不是原始字节比较：

```bash
skopeo inspect --raw "docker://${src}"  | jq -S -c .    # -S 排序键，-c 紧凑输出
```

直接比字节会因为 JSON 键顺序不同而误判（不同工具生成的 manifest 键序可能不一样），排序后再比才是语义层面的相等。

**所有失败路径都返回「不相等」**——网络抖动、权限不足、目标不存在，一律当作「需要同步」。这个方向是刻意选的：宁可多推一次，也不能因为一次探测失败就错误地跳过本该同步的镜像。

`strip_attestation` 模式不做跳过，因为它会用 `regctl` 重建索引，目标的 digest 必然与源不同，比较没有意义。

### 为什么并发用子进程 + 结果文件

**因为要守住「本地和 CI 跑同一份代码」这条线。**

引入 Python 或 Go 能获得更好的并发原语，代价是使用者本地必须装运行时——而本地可验证恰恰是这个项目的核心设计目标。bash 的 `&` 加 `wait` 足以覆盖这里的并发需求。

代价是结果收集不能用数组：**子进程对全局数组的修改不会传回父进程**。所以每个镜像把结果写进一个以序号命名的临时文件，全部结束后再按序读回。这保证了并发模式下**结果表的顺序仍然与输入一致**——否则用户看到的将是一张随完成顺序乱跳的表格，批量核对时会非常难受。

另外两个兼容性取舍：

- 没用 `wait -n`（bash 4.3+）来等待任意一个作业结束，改用 `jobs -pr` 统计运行中的作业数来控制槽位，否则 macOS 自带的 bash 3.2 会直接报错
- `timeout` 命令是 GNU coreutils 才有的，macOS 上叫 `gtimeout` 且需要额外安装。两个都找不到时**降级为不限制超时并给出提示**，而不是直接失败——超时只是保护措施，不该成为使用门槛

### 为什么镜像筛选「只标记、不删除」

**因为下标同时决定结果文件的序号。**

`--filter` / `--exclude` 命中的镜像如果从数组里删掉，其后所有镜像的下标会整体前移，而结果文件是按「镜像序号-目标序号」命名的——序号错位意味着结果表与输入的顺序对不上，并发模式的顺序保证随之瓦解。所以筛选只是在与 `SOURCE_IMAGES` 对齐的另一个数组里记录排除原因，被排除的镜像照常占位。

顺带解释两个相关决定：被排除项**必须出现在结果表里**并标注原因（清单 20 个、结果 19 行，使用者会以为第 20 个同步了——看得见的排除才是排除）；全部被筛掉时**按参数错误退出 1**（静默地「什么都没同步却报成功」是最糟的结果）。

### 为什么源仓库凭证不经过命令行

**因为命令行参数对同机其他进程可见，也容易被日志语句原样打印。**

`ps aux` 能看到任意进程的完整命令行——密码写在参数里，等于对同机所有用户公开。更现实的威胁是调用方的日志语句：工作流里就有一句 `echo "执行：./scripts/sync.sh ${args[*]}"`，凭证一旦进参数就会被打进 Actions 日志（留存 90 天、对协作者可见）。所以凭证只写进 600 权限的临时文件，经 `--src-authfile` 交给 skopeo，脚本退出即删。

**源与目标的凭证刻意不共用**：目标是你的仓库，源是别人的系统。把目标仓库的凭证发往源仓库，等于把「往我仓库推送」的权限交给一个你并不信任的第三方。被否掉的方案是「默认复用 `DOCKER_USERNAME`，可关掉」——复用应该是显式动作，不该是默认值。

凭证的两种形态（单一凭证 / `--src-credentials` 按仓库映射）**互斥而非叠加**：混用时「文件里有 A 仓库、命令行又给了另一个用户名」的语义只能靠猜。宁可拒绝，让使用者把意图写清楚。CI 场景的 `SYNC_SRC_CREDENTIALS` 环境变量值为**文件内容**而非路径——Secret 是一整段文本，落成临时文件后走同一条解析路径，不为它单独开分支。

host 推导（未指定 `--src-registry` 时）遵循 OCI 引用解析规则：第一段形如主机名（含点、含端口冒号或字面 `localhost`）才算 registry，否则视为 Docker Hub。推导结果列在日志里——凭证被发往了哪些仓库必须可见。

### 为什么完整性校验（--verify）复用跳过判定的平台摘要

**因为两者回答的是同一个问题：「目标的内容与源一致吗」。**

顶层 digest 会因 registry 重新包装 manifest 而变化、Windows 平台的 manifest 在传输中必然重新生成——这两个「内容一致但 digest 不同」的误报源，增量跳过在 v1.1.0 就已经付过学费（比较依据因此改为各平台子 manifest 的 digest、排除 Windows）。校验如果另起炉灶，这些学费就白交了。复用 `platform_digest_map`，两条约束自动继承。

校验拿不到 digest 时返回 2、**不判失败**：网络抖动是常态，让校验成为比同步更脆弱的环节，等于把「附加保障」变成了「单点故障」。与 digest 记录的处理原则一致：拿不到就留空/告警，不影响成败。

「目标与源不一致」这个场景**无法稳定端到端构造**——校验紧跟同步执行，同步本身会覆盖掉不一致的目标。因此判定逻辑用 mock 单测（mock `skopeo_inspect_raw` 这个唯一入口，平台提取仍走生产代码），真实路径由集成测试验证「一致 → 校验通过」。

### 为什么通知阈值从历史报告推算，而不是保存状态

**因为「不引入新的存储」是这个项目已经确立的约束，而报告 Artifact 本来就在那里。**

被否掉的方案有两个：往仓库（或独立分支）写状态文件——只增不减、无法清理，违反「历史的价值在于趋势，而趋势不需要永久保存」；用 `history.sh` 直接复用——它是独立的事后查询工具，不是同步流程的库，为了一个阈值把它变成同步的前置依赖，耦合方向反了。

实际做法：发送通知前用 `gh run download` 拉最近 15 次运行的报告，逐镜像从最新往回数连续 `failed`。三个配套决定：

- **历史只在「有失败且阈值 > 1」时才下载**——不让每次成功的运行都付出这几秒
- **拿不到历史一律按「连续失败 1 次」处理**——宁可不通知，也不基于猜测误报
- 单个工作流传入自己的 Artifact 名（`sync-report-*`）——名字对不上就拿不到历史，这是契约而非巧合

### 为什么 history.sh 只读报告 Artifact

**因为持久化的历史是负债，聚合已有数据是收益。**

为看趋势而往仓库里持续提交历史文件，代价是一个只增不减、几乎无法清理的提交记录。而每次运行本就上传报告 Artifact，读回来聚合即可——不需要新存储、不污染提交历史。代价是历史窗口等于 Artifact 保留期（30 天），这个取舍是值得的：30 天足够回答「这个镜像是不是一直在失败」。

实现上有一个容易做错的细节：「最近一次」按报告内的 `generated_at` 取，**不是**按文件顺序——下载顺序与运行时间未必一致，而这恰恰是使用者最依赖的一列。

### 为什么多目标中转是「纯优化」

**因为失败可定位是多目标同步的核心价值，任何优化都不能侵蚀它。**

v1.2.0 引入多目标时，文档如实记录了「源镜像会被拉取多次」的取舍。v1.5.0 用本地 OCI 中转把它优化掉：源拉取一次，逐目标推送。但优化的边界被严格限定——**中转准备阶段的任何失败都退化为逐目标拉推的旧行为**：

- 磁盘空间预检不足（按估算大小 × 并发度放大）→ 告警 + 退化
- 拉取失败 → 告警 + 退化，每个目标独立重试

结果记录的语义在任何情况下不变：每目标独立成败、独立跳过判定。被否掉的方案是以第一个目标为中转——快，但第一个目标成了单点，它失败则后面的全部失败，这正是优化最容易引入的故障传染。

同样从学费里继承的还有：中转推送的 `--all` 不能省（多架构索引），拉取段带 `--src-authfile` 与源 TLS 设置（否则私有源的中转静默失效——与跳过判定失效是同一类病根）。

单目标不走中转：没有收益的改动不该做，CI 里有负断言守住这一点。

### 为什么把「检查」与「搬运」拆开

**因为「该同步什么」和「把镜像搬过去」是两个问题，而后者有副作用。**

在此之前，「我的仓库跟上清单了吗」只有真的跑一次同步才能回答——而同步是会真推送的。「想知道状态」被迫付一次「产生副作用」的代价，这在语义上就不对等：只读的问题不该需要写权限。

`--audit`（目标 vs 清单）与 `--check-updates`（上游 vs 清单）把这两个问题独立出来：不推送、可以随时跑、不需要目标地址（后者）。被否掉的方案是「给同步加一个 `--check-only` 开关」——同一个命令承担两套完全不同的输出与退出码语义，调用方每次都要先判断「这次它到底会不会推送」，这比多一条命令更难用对。

### 为什么「无法判定」必须单独成一类

**因为把「查不到」显示成「落后」，会让人去排查一个并不存在的问题。**

审计要回答「目标仓库有没有这个镜像」，而这个问题的失败方式有三种：目标确实没有（缺失）、目标有但内容不同（落后）、**根本查不到**（网络抖动、凭证失效、私有仓库权限）。第三种在前两类里都放不下。

这带来一个取向问题：判据该保守还是激进？`probe_ref` 选择**保守**——只有 registry 明确表示「不存在」的错误才算缺失，其余一律算无法判定。

依据是两种误判的代价并不对称：把「查不到」报成「缺失」，会诱导使用者去同步一个可能早就存在的镜像（白费带宽，还让人以为自己仓库有问题）；反过来把「真的缺失」报成「无法判定」，只是少了一次提示，下个运行周期就能发现。**错误的信息比没有信息更糟，因为它会被当成结论。**

同理，源镜像自身取不到时报的是「无法判定」，而不是目标「缺失」——源都读不到，任何关于目标的结论都无从谈起。

### 为什么 `--audit` 与 `--strip-attestation` 互斥，而且直接报错

**因为剔除 attestation 会重建索引，目标的平台摘要必然与源不同，审计只会给出一排假的「落后」。**

审计判定「最新」的依据是逐平台比对子 manifest digest（与 `--verify`、增量跳过同一套）。而 attestation 剔除路径用 `regctl index create` 重建索引，目标 digest 与源不同是**预期行为**，不是问题。

继续跑不会崩，只会输出一堆看起来像问题的正常现象。这比直接失败更糟：它会引导人去做错误的排查。所以这里 `die` 而不是告警后继续——**能预见到输出会误导人时，就该拒绝执行**。

### 为什么上游版本检查不做语义化版本判断

**因为上游 tag 的命名并不规整，语义化比较会给出错误结论。**

`--check-updates` 报告的是「上游有这个 tag 而清单没有」。要把它做成「建议升级到 X」，就得回答「哪个 tag 更新」——而这需要对 tag 排序。

被否掉的方案有两个：

- **写一个 semver 比较器**：上游大量 tag 不符合 semver（`1.27-alpine`、`3.5.15-0`、`latest`、`v1.32.0-rc.1`），解析失败的只能跳过或猜，两种都会给出错误结论；而「正确的比较规则」在不同仓库之间并不通用
- **用正则筛 `^v?[0-9]` 再比较**：看起来能过滤噪音，实际会把 `1.27-alpine` 这类变体一起选中，再和主版本混排

所以这里只做一件事：用 `sort -V` 做「谁在后」的**粗排序**，原样展示，并明确写出「这不是升级建议」。代价是输出里会出现 `latest`、甚至比清单里更旧的 tag——这是刻意的，它只陈述「上游有这个 tag」这一个事实。**哪个版本能上生产涉及兼容性判断，是使用者的决定，不是工具的。**

### 为什么两条只读检查互斥，而不是一次跑完

**因为检查对象不同，报告是两套，混着跑会互相淹没。**

`--audit` 看的是「目标仓库与清单的差距」（逐镜像 × 逐目标），`--check-updates` 看的是「上游与清单的差距」（逐源仓库）。两者的结果结构、计数口径、退出码含义都不同。

合并成一次输出需要设计一套复合报告，而使用者真正想问的往往是其中一个问题。分两次跑的成本是一条命令，合并的收益抵不上这份复杂度。

### 为什么退出码 2 同时包含「有差异」与「没查完」

**因为 CI 门禁不该在检查本身没做完时报绿。**

审计的退出码是 `0` 全部最新 / `1` 参数或环境错误 / `2` 未得出「全部最新」——**既包括存在落后、缺失、无法判定，也包括有仓库根本没查成**。

把「没查完」也归入 2，是因为这两种情况对使用者是同一件事：**你现在不能相信「一切正常」这个结论**。如果「没查完」返回 0，一次网络抖动的运行会让门禁报绿，而那恰恰是最不该被信任的一次运行。

具体属于哪一种，报告正文里分得很清楚（各类状态分开计数），所以合并到退出码上没有丢信息。

### 为什么镜像命名规则挂在每个目标上，而不是全局一份

**因为「哪个目标需要压平」是目标自身的属性，不是这次运行的选择。**

压平规则（`/` → `_`）的存在理由很具体：阿里云 ACR 个人版不支持多级仓库路径。而自建 Harbor 支持多级路径，保留原路径更符合直觉。于是「阿里云给国内集群 + Harbor 做内部归档」这个最典型的多目标场景，两边要的名字天然不同。

被否掉的方案是给 `--dest` 加一个 `--flatten yes/no` 的全局开关——那只是把「其中一个目标必须将就」换了个写法。规则挂在目标上之后，`--dest` 与 `--dest-keep-path` 可以任意混用、顺序无关。

实现中撞到一个边界：仓库路径不允许出现冒号，所以源 registry 带端口时（`localhost:5000/foo`），端口那一段在两种模式下都会压成下划线。这不是压平规则的一部分，而是 registry 语法本身的约束——保留路径模式保留的是**层级结构**，不是「原样照抄」。（这个边界是写 CI 测试时发现的：本地 registry 恰好是 `localhost:5000`，一跑就露。）

### 为什么不给体检加定时触发器

**因为「什么时候访问上游」是使用者的决定，不是项目替他做的决定。**

`--audit` 与 `--check-updates` 是只读的，技术上可以安全地定时跑。但项目对「自动触发」的克制不只针对推送：一旦工作流自己决定何时去访问一批上游仓库，使用者就失去了对「谁在什么时候碰我的凭证」的完整知情。

所以体检工作流只有 `workflow_dispatch`。需要定时的使用者可以 fork 后自行加一行 `schedule`——那时决定是他做的，风险也是他评估的，文档只负责说明怎么做。

### 为什么锁文件时效审计查上游，而不是比对本地

**因为本地没有可比对的东西——`--write-lock` 只完成了「能复现」这半件事。**

锁文件记录的是「当时锁的 digest」这一历史事实，它自己永远「正确」；会失效的是它与上游现实的关系。上游重新构建并覆盖同名 tag 时，锁文件一个字节都不会变，而下一次增量同步发现源变了，会把新内容**静默搬进你的仓库**——等你在集群行为异常时发现，已经隔了很久。缺的环节是定期问一句「上游的 tag 还是我锁的那份吗」，这只能去问上游。

比对口径与 `--write-lock` 完全同源（都是 `compute_digest` 的顶层 manifest digest），所以「一致」意味着的正是「当时锁的就是这份」，而不是另一套判据下的碰巧相等。

边界：「上游 tag 已删除」算漂移而不是无法判定——tag 消失是明确发生的变更（registry 明确回答了「不存在」），要与「网络原因查不到」区分开。这延续的是「无法判定必须单独成类」的同一原则。

### 为什么检查报告要落盘

**因为跑完什么都不留的检查，趋势就无从谈起。**

`--report-dir` 让三种检查（审计 / 上游发现 / 锁文件校验）与同步报告对齐：`.md` 给人看（与 Step Summary 同源），`.json`（`generated_at` / `check` / `summary` / `records`）机器可读。体检工作流把它上传为 `check-report` Artifact——`history.sh` 的整个数据模型是「读回历次报告 Artifact 做聚合」，检查报告不落盘，检查类趋势就永远没有数据源。

被否掉的方案是为检查单独设计一套云端汇总存储——违反「不引入新的存储」：报告 Artifact 本身就是现成的数据源，读回来聚合即可。

### 为什么锁文件时效校验要上云

**因为校验动作本身也要能被趋势化，而趋势的入口在 Actions 页面。**

`--audit-lock` 做出来时只能在本地命令行跑，而项目的主力使用者是通过 Actions 页面操作的——v1.7 补仓库体检工作流，补的就是这个断层。体检工作流的 `mode` 增加 `lock` 档之后，锁文件时效校验在云端可跑、可复查，报告进同一个 `check-report` Artifact，`history.sh --check lock-audit` 的「哪个锁条目一直在漂移」才有连续数据可聚合。

权限上的细节：`updates` 与 `lock` 模式只查上游、完全不碰目标仓库，因此不需要目标仓库的登录凭证——校验动作用不到的凭证就不该被携带。

### 为什么 `--check` 做趋势聚合，`check-updates` 明确不做

**因为不是所有数字都有趋势价值——「未收录 tag 的增减」没有。**

audit 趋势回答「哪个镜像一直落后 / 一直缺失」，lock-audit 回答「哪个锁条目一直在漂移」：两者都是同一个条目跨运行的**持续状态**，正是趋势要回答的问题。而 `check-updates` 报告的是「上游有而清单未收录的 tag」——这次有、下次没有，反映的是上游的发版节奏与清单的收录决策，不是需要盯防的漂移；把它做成趋势只会产出一片噪音。

所以 `--check check-updates` 直接报参数错误，并在文案里写明理由。另一个容易踩的取数细节：`--check` 默认只看 `Check-Registry` 工作流的运行——体检是低频的手动触发工作流，不限工作流的话，最近 N 次运行几乎全是 CI / Scorecard 这类高频运行，一份检查报告都捞不到。**这不是数据不存在，是取数范围选错了。**

### 为什么趋势结果落盘 md + json 双份，聚合口径要单一来源

**因为落盘的 json 是下一次聚合的原料，口径漂移会让趋势自己骗自己。**

`.md` 与 stdout 同源（可直接粘进 Issue 或文档），`.json`（`generated_at` / `query` / `summary` / `rows`）机器可读，供 History-Trend 工作流留档。产物按查询模式命名（`sync-trend` / `audit-trend` / `lock-audit-trend` / `slowest-trend`），与 `sync.sh` 的 `<check_name>-report` 同一约定。

关键约束在代码结构上：渲染函数与落盘共用同一组聚合函数（`sync_trend_counts` 与各 `*_trend_rows`），**在这里各定义一次，调用方只消费结果**。直接复制 jq 字符串让渲染和落盘各算各的，两张表会悄悄漂移——「同源」就成了空话。

### 为什么下载失败要与「无附件」区分

**因为「数据不存在」和「数据拿不到」是两种完全不同的排查方向。**

`history.sh` 的下载循环最初只区分成功与失败，失败一律静默跳过——理由本身是对的（CI / Release 运行本来就没有报告附件，跳过是常态），但把「带附件却被网络抖动中断」也静默吞掉后，最终报错是「这 N 次运行里没有任何附件」，引导人去查「工作流有没有跑过」——而它跑过（真实踩到：v1.10 验证下载窗口修复时，本机对 Artifact 的 Azure Blob 端点间歇性 EOF）。

现在按 `gh` 的报错原文先分类（两条「无附件」文案归正常），拿不准的用 artifacts API 二次确认：有附件但下载失败的如实计入汇总并提示可重试，附件已按保留期清理的如实说明，无附件照旧跳过。API 也查不动（网络不稳）时，计入「应下载却失败」而不是冒充正常——**未知不冒充已知，失败不冒充缺失**，这是「无法判定必须单独成类」原则在下载路径上的又一次落地。

### 为什么报告下载的重试放在主循环之后，且只重试一轮

**因为批量本身已经形成退避，而持续抖动不是脚本该解决的问题。**

失败项集中在主循环结束后重试，其余运行先下载完；每个失败项之间再固定等 5 秒。只重试一轮——实测连续 5 次整命令重跑仍失败属极端环境，如实报错加 `--dir` 兜底已经足够。

重试次数与间隔**不做参数化**：为极少调整的值增加表面积不划算，新参数还得进「显式传入不生效告警」矩阵。被否的方案是「原地重试」（失败当场重试，而不是攒到主循环之后）：立即重试可能仍在抖动窗口内，而且会拖慢正常路径——其余运行下载完再回来，时间间隔天然被拉开。

### 为什么重跑指引给锚定正则，而不是给 Sync-Batch 加一个输入框

**因为要动的面越小越好，而 `filter` 本来就够用。**

同步失败后要重跑，使用者得先把失败项挑出来。Aliyuncs / Harbor 有 `images_src` 自由文本输入，粘一份镜像列表就行；`Sync-Batch` 没有——只有 `lockfile`（仓库内路径）与 `filter`（正则）。

考虑过给它补一个「直接指定镜像」的输入。否掉的理由有两条：那要改工作流 YAML，而工作流有 zizmor / actionlint 门禁、本项目历史上批量改 YAML 连续出错过；更关键的是 `--src` 与 `--file` 在 `sync.sh` 里是**合并**语义，新输入与 `lockfile` 究竟是替换还是叠加需要额外解释——**没有收益的改动不该做**。

锚定正则可完全复用现有输入，但有三处不处理就会变成一条会误伤的指引：

- **必须锚定**——`--filter` 走 `grep -E`，是**部分匹配**；不锚定则 `nginx:1.27` 会把 `nginx:1.27-alpine` 一并匹配进来
- **必须转义 ERE 元字符**——镜像引用里点号几乎必然出现，不转义等于让每个点变成通配
- **必须容忍 `docker://` 前缀**——`filter` 匹配的是**规范化之前**的原始串，而清单里的引用取自规范化之后的结果，两者可能差一个前缀

于是生成的是 `^(docker://)?(nginx:1\.27|redis:7\.2)$`，并在渲染前用同一条 `grep -E` 自检语法；自检不过就退回镜像清单形态——**宁可不给正则，也不能给一条把作用域指偏的**。

判定「这条失败重跑有没有意义」用的是内存里的 `R_NOTE`（失败原因里只有「镜像引用格式错误」是重跑也解不了的）。被排除的项不静默消失，指引里带一句计数。注意这里只**借用** `R_NOTE` 做判定，并没有改变它的落盘行为——把失败原因写进报告是独立的一件事，见 [#102](https://github.com/nicholyx/action-sync-images/issues/102)。

### 为什么失败原因要进报告、Summary 与通知

**因为「终端知道、报告不知道」是一种不对称，而报告正是被留下来反复看的那一份。**

`R_NOTE` 此前只在终端表格里打印一次。同一份运行，日志里知道为什么失败，落盘的报告、Actions 页面的 Step Summary、群里的通知都不知道——三种只读检查的报告都带 `note`，唯独同步主模式没有。

这不只是「信息少一点」：`镜像引用格式错误` 与 `同步失败，详见上方日志` 是完全不同的处境，前者重跑多少次都不会成功，后者值得重跑。看不到原因的读者无法区分二者，上一条的重跑指引也就落不了地。

字段语义与 `rerun` 三个字段同一约定：**始终存在**，无原因时为空字符串，消费方不必判空。

### 为什么 `gh run list` 的失败要重试一轮再报错

**因为网络抖动是这条路径的常态，重试能真的省掉一次人工重跑。**

原来的写法是 `done < <(gh run list … 2>/dev/null || true)`：进程替换**不传递退出码**，`|| true` 又把失败吞掉——网络 EOF 时得到空输出，与「这个仓库确实没跑过」混成同一种结果，报错还引导人去查「工作流是不是没跑过」。这与「下载失败冒充无附件」是同一族：**网络问题冒充「数据不存在」**。

重试一轮的取舍与报告下载的重试同口径（固定间隔、不做参数化）。**真正空列表的文案逐字未变**，也不触发重试——那个诊断在退出码为 0 时是准确的。

### 为什么 dry-run 的判据是「有没有真的搬过」

**因为「这段代码跑了多久」与「有没有搬过东西」是两回事，而只有后者决定输出该不该有值。**

`--dry-run` 没有推送任何镜像，但 `process_one` 的计时区照常包住 `sync_to_dest`——而后者在 dry-run 下只打印一行命令就返回。测到的是「打印一行花了多久」：微秒级，够快，只有在负载高的 runner 上才会跨过 1 秒边界。

后果是一个偶发的 `1s`：它进报告 json、进 md 与 Step Summary 的耗时列，并让 `duration_ranking_rows` 输出一份「最慢的同步记录」——**一次什么都没搬的运行报出了耗时排行**。CI 里「耗时全为 0 时排行应隐去」那条断言因此偶发误报，2026-09-19 曾在一次 PR 上把整个 smoke-test job 带崩（重跑即绿）。

同一个判据还清掉了另外三处：不写锁文件、不发通知、不记录目标 digest。

**一处刻意的例外**：`sync.sh` 的「总耗时：N 秒」在 dry-run 下照常显示——它描述的是**进程**跑了多久（进程确实跑了那么久，这是事实），且不进报告。判据是「这条输出描述的是搬运还是进程」。

### 为什么 dry-run 下锁文件与通知是「不生效 + 告警」，而不是产出「dry-run 版」

**因为这两件事的对象都是「一次真实的搬运」，而干跑没有对象。**

锁文件记录的是「这次推上去的是哪一份」，通知通报的是「这次搬得怎么样」。给它们做一个「dry-run 版」等于发明一种新的产物语义：锁文件拿去回喂 `--file`，会让人以为复现的是当时推上去的那份；通知的正文写着「镜像同步完成……失败 N 个」，**收到的人会去排查一件根本没发生的事**。

所以按项目既有的处理模式（`--audit-lock` 忽略无关参数的做法）：**不生效 + 告警**，多个参数合并成一条、一次列全，并说明怎么办（去掉 `--dry-run`）。只在参数真被传入时告警——「默认值不生效不打扰，显式传入必须说」。

只读检查模式（`--audit` / `--check-updates` / `--audit-lock`）不受影响：那里的 `--dry-run` 本就按既有语义忽略，通知照常发出。

### 为什么报告加 `dry_run` 字段，而不是改 `status` 的取值

**因为要回答的问题是「这份报告是不是干跑产出的」，而不是「这次搬运的每个镜像成功没有」。**

dry-run 的报告里每条镜像都是 `status: success`，但它描述的是计划。消费方（`history.sh` 的四处聚合、`sync.sh` 的 `fetch_sync_history`）只看文件内容，无从知道它是怎么跑出来的——`status` 本身没有说谎，它只是**没回答那个问题**。

改 `status` 会波及全部消费方与多条既有断言，而问题出在**报告的来源**上，不在单个镜像的状态上。顶层加一个 `dry_run` 布尔字段，判据精确、改动最小。

两个必须守住的细节：**缺该字段的旧报告视为真实运行**（升级不该让历史数据失效）；**dry-run 报告照常落盘**（它是计划，有独立价值），只改「历史聚合要不要算它」。

漏掉这层过滤的后果比看上去重：`count_consecutive_failures` 遇到任何非 failed 记录即清零，**一次干跑的 `success` 足以压掉一个真实存在过的失败序列本该触发的告警**。

## 安全模型

本仓库最核心的风险是：**工作流里存放着真实可用的镜像仓库推送凭证。**

完整的威胁模型、已采取的防护措施、以及「怀疑凭证泄露时怎么办」，都写在 [SECURITY.md](../SECURITY.md) 中，请务必阅读。

这里只强调两条与改代码直接相关的铁律：

1. **不要给工作流添加自动触发**（`push`、`pull_request`、`issue_comment` 等），除非你能保证该路径下不可能执行到未受信任的输入。当前所有同步工作流都只有 `workflow_dispatch`，这是有意为之。
2. **不要把 `${{ }}` 表达式直接写进 `run:`**。必须先落到 `env:`，再用带引号的变量引用。CI 中的 `actionlint` 会拦截一部分这类问题，但它不是万能的。
